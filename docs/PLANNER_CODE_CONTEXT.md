# TFT Planner Code Format

## Overview

A **planner code** is the string the TFT in-game Team Planner reads. We emit
real Riot codes — the kind that paste directly into the client — instead of a
custom JSON+base64url codec.

The format ends with the literal suffix `TFTSet<N>` where `N` is the current
set number. For the current build that's `TFTSet17`. If the suffix in a code
you've copied doesn't say `TFTSet17`, the code was generated by an outdated
build.

---

## Wire format (current — v02)

```
02 + <28 × 2 hex chars> + TFTSet<N>
```

| Segment | Length | Meaning |
|---|---|---|
| `02` | 2 chars | Version prefix (constant for Set 9+) |
| Board state | 56 chars | 28 bytes, one per board position. Each byte is the champion's `team_planner_code` from CDragon's `tftchampions-teamplanner.json`. Empty positions are `00`. |
| `TFTSet<N>` | 8 chars (for Set 17) | Literal set suffix. The TFT client uses this to pick the right per-set champion lookup table. |

**Set 17 total length: 66 chars** (2 + 56 + 8).

### Board position layout

```
col:  0   1   2   3   4   5   6
row 0:  0   1   2   3   4   5   6   (back row — hexes furthest from enemy)
row 1:  7   8   9  10  11  12  13
row 2: 14  15  16  17  18  19  20
row 3: 21  22  23  24  25  26  27   (front row)
```

Position = `row * 7 + col`. Valid range: 0–27.

---

## Example

Board: Jinx (team_planner_code 18 = 0x12) at position 3 + Ahri (1 = 0x01) at
position 10 + Galio (39 = 0x27) at position 24, Set 17.

```
0200000012000000000000010000000000000000000000000027000000TFTSet17
```

Breakdown: `02` + `00 00 00 12 00 00 00 00 00 00 01 00 00 00 00 00 00 00 00 00 00 00 00 00 27 00 00 00` (spaces added for readability) + `TFTSet17`.

---

## What is preserved / lost

The in-game format encodes **only champion positions**. It does NOT preserve:

- Star levels
- Equipped items
- Augments
- Notes / metadata

That's a limitation of the TFT client, not our implementation. Star/item/augment
state stays in the guide's JSONB `board_steps` record — the planner code is
just one export view.

## Implementation

### Files

| File | Role |
|---|---|
| `src/features/tft-data/planner-code.ts` | Encode / decode codec — also runs a roundtrip self-test in development builds |
| `src/features/tft-data/use-tft-data.ts` | Fetches the team-planner JSON at app load; exposes `plannerCodeMap` |
| `src/features/tft-data/normalize.ts` | Accepts `teamPlannerCodes` in `NormalizeOptions`; attaches `plannerId` to each `TFTChampion` |

### Data flow

1. `useTFTData()` fetches CDragon TFT data + DDragon augments + team-planner JSON in parallel.
2. The team-planner JSON's `TFTSet<CURRENT_SET>` array yields a `{character_id → team_planner_code}` map.
3. `normalizeSetData` attaches `plannerId` to each `TFTChampion` from that map.
4. The hook returns `plannerCodeMap: Map<apiName, number>` for consumers.
5. `generatePlannerCode(units, setNumber, plannerCodeMap)` produces the code string.
6. The codec runs an encode→decode roundtrip on a fixed fixture at module load in development to catch regressions.

### Encoding logic (`generatePlannerCode`)

1. Validate inputs (non-empty board, valid set, non-empty map).
2. Allocate a 28-element byte array, all zeros.
3. For each unit:
   - Validate position is in [0, 27].
   - Look up `team_planner_code` in `plannerCodeMap`.
   - Skip with warning if missing / out of byte range / equals 0 (collides with empty marker).
   - Write the byte to `bytes[position]`.
4. Hex-encode (uppercase, zero-padded).
5. Concatenate: `02` + hex + `TFTSet<setNumber>`.
6. Self-validate against the canonical regex before returning.

### Decoding logic (`decodePlannerCode`)

1. Strip whitespace, match `/^02([0-9A-Fa-f]{56})TFTSet(\d+)$/`.
2. Parse `set` from the suffix capture.
3. Build a reverse map (code → apiName) from the input `plannerCodeMap`.
4. Walk the 28 bytes; for each non-zero byte, look up the apiName.
5. Return `{ set, units: [{ championKey, position }] }`.

Codes that don't match the canonical regex produce `{ ok: false, error }` with a helpful preview of what was actually received.

## Validation

Self-test runs in development builds only (gated on `process.env.NODE_ENV !== "production"`, Vite strips the entire block at build time):

```typescript
const fixtureMap = new Map([
  ["TFT17_Jinx", 18],     // 0x12
  ["TFT17_Ahri", 1],      // 0x01 — exercises single-digit padding
  ["TFT17_Galio", 39],    // 0x27
]);
const fixtureUnits = [
  { championKey: "TFT17_Jinx", position: 3, ... },
  { championKey: "TFT17_Ahri", position: 10, ... },
  { championKey: "TFT17_Galio", position: 24, ... },
];
```

Expected output: `0200000012000000000000010000000000000000000000000027000000TFTSet17`

Encode produces that exact string; decode returns the original three units. Mismatch logs `[planner-code self-test] roundtrip MISMATCH` to the console.

## Manual / production verification

To verify a code is actually accepted by the TFT client:

1. Build a board in the app.
2. Click "Copy board code".
3. Paste into the TFT client's Team Planner UI (Customize tab → Import).
4. Confirm: champions appear at the same positions; the set selector matches; no "invalid code" error.

If verification fails:

- Check the console for `[planner-code]` warnings about missing `team_planner_code` entries.
- Check `[TFT] Team-planner map: N entries for TFTSetXX` — N should be ≥ 60 for Set 17.
- Verify the suffix on the copied code says `TFTSet17`, not `TFTSet14` / earlier.

## Future considerations

If a future set introduces champion codes > 255, the byte-per-position format
breaks. Symptoms: encoder skips champions with `team_planner_code` warnings,
self-test mismatches. The fix at that point is to bump the version prefix
(e.g. `03`) and use 2 bytes per position. Until then, the 1-byte format
matches what the TFT client actually accepts.

If you bump `CURRENT_SET` in `normalize.ts`, also bump the same constant in
`use-tft-data.ts` (next to the team-planner fetch). Both feed into the
`TFTSet<N>` suffix.
